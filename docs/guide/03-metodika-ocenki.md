# 3. Методика оценки

Раздел отвечает на три вопроса ТЗ 3.4: как устроено тестирование и почему оно устойчиво к распространению заданий, как работают категоризация и подбор, как команда проверяла решение и что получилось. Все числа ниже пересчитываются командой `PYTHONPATH=src python scripts/validate.py`; полный отчёт — [docs/validation/results.md](../validation/results.md).

## Почему не единый набор и не задания от нейросети

ТЗ отвергает оба очевидных пути (п. 2):

| Подход | Проблема |
| -- | -- |
| Единый набор заданий | Ответы расходятся по рынку за недели. В нашей симуляции утечка единственного варианта даёт слабому кандидату 100 % прохождения |
| Уникальные задания от LLM под каждого | Сложность и объективность между кандидатами не гарантированы: модель может сгенерировать задачу проще или с ошибкой в ответе, и сравнить кандидатов уже нельзя |

HyreKit берёт лучшее от обоих: задания уникальны, как у генерации, но собираются из **откалиброванных генераторов**, а ответ вычисляет код, а не модель.

## Банк параметрических заданий

Банк (`src/app/assessment/bank.py`) хранит не вопросы, а **36 семейств** — генераторов по 14 темам: алгоритмы, Python, JavaScript, веб, HTTP, SQL, архитектура, ML, статистика, Linux, сети, контейнеры, тестирование, безопасность.

Семейство по зерну (`seed`) и уровню сложности (`level` 1–5) порождает конкретное задание: другие числа, данные, имена, код, порядок вариантов. Правильный ответ вычисляется тем же кодом. Пример — семейство `http_backoff`:

> Каждый запрос к API завершается таймаутом через 500 мс. Клиент делает первую попытку и до 3 повторов с экспоненциальной паузой: первая пауза 330 мс, каждая следующая в 2 раза больше. Через сколько миллисекунд от начала клиент сдастся?

У следующего кандидата будут другой таймаут, другая пауза, другое число повторов; на уровне 4 добавится потолок паузы, на уровне 3 — множитель 3. Выученное «правильное число» не переносится, перенести можно только понимание.

Форматы ответов: один вариант, несколько вариантов, число. Задачи с кодом — вывод программы, сложность алгоритма, результат SQL-запроса, ширина flex-элемента, права `chmod`, широковещательный адрес подсети.

### Два класса семейств

| Класс | Сколько | Что проверяет | Пространство вариантов |
| -- | -- | -- | -- |
| Генеративные | 23 | Навык: вычислить, предсказать вывод, разобрать данные | Практически бесконечное |
| Концептуальные | 13 | Знание понятия: идемпотентность методов, паттерн, уязвимость в фрагменте | Конечное, формулировки повторяются |

Концептуальные задания быстро «выучиваются» рынком, поэтому в плане попытки первое задание каждой темы всегда генеративное, а концептуальных не больше одного на попытку (`engine.MAX_CONCEPTUAL`). Это решение принято по результатам атаки утечкой, см. ниже.

## План попытки и равная сложность

Попытку собирает `engine.build_blueprint(specialization, grade)`:

1. Берутся 5 тем специализации (у Backend — алгоритмы, Python, SQL, HTTP, архитектура).
2. На каждую тему 2 задания: уровень грейда (`order + 1`) и соседний уровень — на чётных темах выше, на нечётных ниже.
3. Для каждого слота случайно выбирается семейство, допустимое на этом уровне (у семейства есть минимальный осмысленный уровень), и случайное зерно.
4. Задания перемешиваются; на попытку 10 заданий и 20 минут.

Профиль сложности — мультимножество уровней — определяется только грейдом. У всех кандидатов, тестируемых на Middle, он один и тот же: `[2, 2, 3, 3, 3, 3, 3, 4, 4, 4]`. Валидация собирает по 1 200 случайных вариантов на каждый грейд и проверяет это по уровням **сгенерированных** заданий: различных профилей — ровно один.

План попытки (семейства, уровни, зёрна) хранится в базе, поэтому попытку можно продолжить после перезагрузки, а результат — перепроверить.

## Оценка способности и решение по грейду

Ответы переводятся в оценку способности θ по модели Раша (однопараметрическая IRT): вероятность верного ответа на задание сложности `b` равна `σ(θ − b)`, где `b = level − 3`. Оценка — MAP с априорным N(0, 1), метод Ньютона (`engine.estimate_ability`).

Пороги грейдов на шкале θ: `cut(g) = order(g) − 2.5`, то есть Intern −2.5, Junior −1.5, Middle −0.5, Senior 0.5, Lead 1.5. Коридор каждого грейда — один логит.

Решение (`engine.decide`) следует ТЗ:

| Исход | Что происходит |
| -- | -- |
| θ ≥ порога тестируемого грейда | Грейд присвоен, категория `специализация:грейд` видна работодателям |
| θ ≥ порога следующего грейда + 0.35 | Плюс подсказка «попробуйте уровень выше» |
| θ ниже порога | Грейд **не понижается**, предлагается тест уровнем ниже |
| У кандидата уже есть более высокий грейд | Он сохраняется — результат слабее не отнимает подтверждённое |

Смена грейда — не чаще раза в 90 дней (`GRADE_COOLDOWN_DAYS`). Пока грейда нет, можно пробовать любой уровень сколько угодно раз: так кандидат, не сдавший заявленный уровень, сразу сдаёт уровень ниже.

Помимо θ кандидат видит балл 0–100 (доля верных, взвешенная по сложности) и разбор по темам.

## Категоризация и рейтинг внутри категории

Категория — связка специализации и подтверждённого грейда: «Backend · Middle». Она задаётся **только тестом**; самоописание из резюме и анкеты на неё не влияет (ТЗ 2.1, требования к подбору).

Внутри категории кандидаты ранжируются по силе подтверждённого профиля (`candidates.service.rating`):

| Компонент | Вес | Как считается |
| -- | -- | -- |
| Результат теста | 65 % | `100 · σ(1.5 · (θ − cut(грейд)))` — насколько уверенно кандидат прошёл порог своего грейда |
| Достижения ФСП | 25 % | Балл 0–100: уровень соревнования × место × давность; дисциплина, профильная для специализации, весит вдвое больше |
| Свежесть | 10 % | 100 в течение 30 дней после активности, затем линейно до 0 к 180 дням. Активность — тест, правка профиля, ответ на короткое задание |

Кандидат без истории ФСП получает 0 по этому компоненту и ранжируется по тесту и свежести — профиль обрабатывается корректно, как требует ТЗ.

## Механика подбора

Работодатель описывает потребность: специализация, диапазон грейдов, стек, описание задач и команды, вилка зарплаты. Подборка (`matching.service.match_vacancy`) строится так:

1. **Кандидатный пул** — видимые профили нужной специализации: есть категория и согласие на публикацию.
2. **Требуемый стек** — стек вакансии плюс технологии, найденные в тексте описания (синонимы нормализуются: `k8s` → Kubernetes, `postgres` → PostgreSQL).
3. **Балл соответствия 0–100**:

| Компонент | Вес | Как считается |
| -- | -- | -- |
| Категория | 30 % | Грейд в диапазоне — 100; на ступень выше — 70 (запас квалификации); на ступень ниже — 55 (потенциал роста); дальше — 0 |
| Стек | 30 % | Доля требуемых технологий, которые есть у кандидата |
| Уровень по тесту | 25 % | Насколько измеренная θ попадает в коридор вакансии: внутри — 100, снаружи гауссово затухание с σ = 0.5 логита |
| ФСП | 10 % | Балл достижений |
| Свежесть | 5 % | Как в рейтинге |

4. **Объяснимость**: к каждому кандидату — причины («Категория Backend · Middle входит в требуемый диапазон», «Стек: 4 из 5 (Python, FastAPI, PostgreSQL, Kafka)», «Тест на грейд: 78/100», «ФСП: 2 соревнования, лучшее место — 1, профильных — 1») и список недостающих технологий.
5. **Уточнение без потери подборки**: фильтры по грейду, обязательному стеку и наличию ФСП применяются к уже построенному ранжированию; в интерфейсе прежний список остаётся на экране, пока грузится уточнённый, и «Сбросить фильтры» возвращает исходный.

Компонент «Уровень по тесту» сравнивает θ с коридором вакансии, а не с порогом собственного грейда кандидата. Так сильный кандидат, которому тест присвоил Middle, но чья θ на уровне Senior, не вытесняет подходящих на вакансию Junior–Middle. Это решение тоже пришло из валидации: с прежней формулой точность подборки для фронтенд-вакансии была 0.73, с новой — 0.89.

## Тест под вакансию

ТЗ просит показать на нескольких описаниях вакансий, как система формирует задания (п. 2). Эндпоинт `GET /employer/vacancies/{id}/assessment` и вкладка «Тест под вакансию» в кабинете работодателя:

1. Каждая технология стека вакансии подтверждает тему теста (`catalog.data.TECH_TOPICS`): Python → Python, PostgreSQL → SQL, Kafka → архитектура, Kubernetes → контейнеры.
2. Темы сортируются по числу подтверждающих технологий; недостающие до пяти добираются базовыми темами специализации. Каждая тема показана с причиной: «Стек вакансии: Python, FastAPI».
3. Строятся два варианта с разными заданиями. Их профили сложности совпадают между собой и со стандартным тестом категории — это проверяет тест `test_vacancy_test_topics_follow_stack_and_keep_difficulty`.

## Регулярные короткие задания

Работодатель публикует задачу для направления («Как сделать платёж идемпотентным?»). Кандидат отвечает текстом. Ответ оценивает GigaChat по рубрике (понимание задачи, корректность, конкретика, учёт рисков); без ключа модели — эвристика по полноте и ключевым словам задачи. Ответ обновляет свежесть профиля и виден работодателю вместе с оценкой.

## Процедура валидации

Готовых датасетов и эталонной разметки в хакатоне нет (ТЗ, п. 2), поэтому команда валидирует методику на **синтетических кандидатах с известной истинной способностью**. Модельный кандидат с θ отвечает на задание сложности `b` верно с вероятностью `σ(θ − b)`. Истинный грейд — наивысший, чей порог не выше θ. Это позволяет измерить то, что на реальных людях потребовало бы экспертной разметки: совпадает ли присвоенный грейд с истинным.

Что проверяется и почему:

| Проверка | Критерий ТЗ | Метод |
| -- | -- | -- |
| Равная сложность вариантов | Сопоставимая сложность между кандидатами | 1 200 вариантов на грейд, считаются различные профили сложности |
| Устойчивость к утечке | Устойчивость к распространению заданий | 200 слитых попыток с ответами на направление; доля дословно совпавших заданий; атака Junior со шпаргалкой |
| Надёжность | Стабильный грейд при повторном прохождении | 400 кандидатов проходят тест дважды независимо; корреляция θ, совпадение решения |
| Дискриминативность | Разделение слабых и сильных | 1 500 кандидатов вокруг грейда, точечно-бисериальная корреляция ответа с θ по каждому семейству |
| Точность категоризации | Соответствие эталонной разметке | 600 кандидатов, 40 % завышают заявленный грейд на ступень; присвоенный грейд против истинного |
| Качество подбора | Доля релевантных в топе на парах «вакансия — кандидат» | 3 демо-вакансии × 20 пулов по 150 кандидатов; precision@10 и nDCG@10 против двух базовых подходов |

### Результаты валидации

**Равная сложность.** У каждого грейда ровно один профиль сложности на 1 200 вариантов.

**Утечка.** По каждому из 6 направлений слито 200 попыток Middle с ответами:

| Показатель | Значение |
| -- | -- |
| Раскрыто генеративных заданий | 3.0 % |
| Раскрыто концептуальных заданий | 52.0 % |
| Раскрытых заданий в попытке из 10, в среднем | 0.8 |
| Junior сдаёт Middle честно | 27.9 % |
| Junior сдаёт Middle со шпаргалкой из 200 попыток | 43.1 % |
| Junior сдаёт статичный тест, у которого утёк вариант | 100 % |

До ограничения концептуальных заданий шпаргалка поднимала долю сдавших до 71 %. Остаточный выигрыш даёт в основном единственное концептуальное задание; его можно убрать совсем (`MAX_CONCEPTUAL = 0`, тогда 33 %), но команда оставила одно ради охвата понятийных знаний.

**Надёжность.** Корреляция θ между двумя независимыми попытками — 0.69, решение «сдал / не сдал» совпадает в 70 % случаев, стандартная ошибка θ — 0.49 логита при ширине коридора грейда в 1 логит. Для теста из 10 заданий это ожидаемый уровень; точность растёт с длиной теста (см. «Ограничения»).

**Дискриминативность.** Медиана корреляции ответа с θ по 32 семействам, попавшим в выборку, — 0.27, минимум — 0.16 (порог пригодности 0.2). Ответы смоделированы по модели Раша, поэтому таблица проверяет конвейер анализа; на пилоте с реальными людьми тот же расчёт покажет семейства для переработки.

**Категоризация** (600 кандидатов):

| Метрика | Значение |
| -- | -- |
| Заявленный кандидатом грейд совпадает с истинным | 63.0 % |
| Присвоенный по тесту грейд совпадает с истинным | **70.5 %** |
| Ошибка не больше одной ступени | 99.5 % |
| Грейд завышен | 6.2 % |

Тест не только точнее самооценки, но и почти не завышает: работодатель получает «Middle», который не окажется Junior. Ошибки — в основном занижение на ступень у кандидатов возле нижней границы коридора; такой кандидат может пересдать через 90 дней.

**Подбор** (precision@10 / nDCG@10, среднее по 20 пулам):

| Вакансия | HyreKit | По заявленному грейду и стеку | Только по стеку |
| -- | -- | -- | -- |
| Python backend, Middle–Senior | **0.87** / 0.86 | 0.80 / 0.79 | 0.59 / 0.58 |
| Frontend React, Junior–Middle | 0.89 / 0.89 | **0.90** / 0.89 | 0.59 / 0.60 |
| DevOps Kubernetes, Middle–Lead | **0.96** / 0.95 | 0.85 / 0.86 | 0.70 / 0.70 |

Подбор по стеку, как на универсальных площадках, даёт 0.59–0.70. Подтверждённая категория поднимает долю релевантных в топ-10 до 0.87–0.96. На вакансии Junior–Middle подбор по заявленному грейду сопоставим с нашим: в узком нижнем диапазоне завышение самооценки на ступень реже выводит кандидата за пределы вакансии.

## Ограничения и что дальше

- Точность грейда ограничена длиной теста: 10 заданий дают ошибку θ около половины коридора. Следующий шаг — адаптивный подбор заданий (CAT) с остановкой по точности: тот же банк, но задание выбирается по текущей оценке θ.
- Сложности семейств заданы экспертно уровнями 1–5. На пилоте их нужно откалибровать по реальным ответам и следить за дрейфом решаемости: если доля верных у семейства растёт без роста θ, его ответы утекли.
- Синтетическая валидация проверяет механику, но не содержательную валидность заданий. Её дадут экспертная оценка выборки реальных кандидатов и сравнение с решениями нанимающих менеджеров.
