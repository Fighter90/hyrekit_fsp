## Как велась разработка

**Источник истины — задачи Linear** в проекте «HyreKit — платформа подбора ИТ-специалистов (ФСП)», ключи `FSP-N`. Эпики повторяют критерии оценки ТЗ: механика подбора (35 %), механика тестирования и категоризация (25 %), интерфейс (10 %), дополнительный функционал (7 %), валидация, документация и сдача.

**Spec-Driven Development.** Путь одной задачи:

1. Задача в Linear: контекст, что сделать, правила и числа со ссылками на пункты ТЗ, критерии приёмки.
2. Спецификация в `docs/specs/fsp-N-*.md` по шаблону [`_template.md`](../specs/_template.md): цель, сценарии, правила, критерии приёмки в формате EARS, план тестов.
3. Контракт API в [`docs/spec/api.md`](../spec/api.md) — до кода; фронтенд и бэкенд пишутся по нему параллельно.
4. Код и тесты на каждый критерий приёмки.
5. Архитектурные решения с альтернативами — в [`docs/decisions/`](../decisions/README.md).

Подробно — [docs/process.md](../process.md).

## Качество

| Что | Как проверяется |
| -- | -- |
| Линтер и формат бэкенда | `ruff check`, `ruff format --check` |
| Тесты бэкенда | pytest, 183 теста, покрытие кода 81 % при пороге 70 % |
| Сквозной сценарий | `tests/test_flow.py`: регистрация → опрос → тест → категория → подборка → приглашение → раскрытие контактов; провал теста без понижения грейда; тест под вакансию |
| Методика | `tests/test_method/`: каждое семейство заданий на всех уровнях генерирует проверяемое задание; монотонность оценки θ; правила грейда; подбор; ФСП |
| Валидация | `scripts/validate.py` в CI: равная сложность, утечка, надёжность, дискриминативность, точность грейда, precision@10 |
| Фронтенд | ESLint, `tsc`, сборка Vite, тесты Vitest |

CI — GitHub Actions, `.github/workflows/ci.yml`: два задания, бэкенд и фронтенд, на каждый push и pull request.
